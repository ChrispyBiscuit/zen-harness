# Agent harness: speed & token-economy plan (local-first)

*Written 2026-10-08. Primary target: local agents on the RTX 3070 8 GB — llama.cpp with Qwen3.6-35B-A3B REAP
(hybrid DeltaNet, experts partly on CPU) and 9B models via llama.cpp / Ollama. API models are secondary.*

## How time is spent on a local model

| What | Speed (35B-A3B, measured) | Consequence |
|---|---|---|
| Reading new prompt tokens (prefill) | ~610 tok/s | an 8k-token tool result ≈ 13 s before the next step starts |
| Writing tokens (generation) | ~19–22 tok/s | 1k thinking ≈ 50 s; a 250-token checklist update ≈ 12 s; the 8k plan budget ≈ up to 7 min |
| Changing anything early in the prompt | full re-read: ≈ 90 s at 57k | this model can't partially rewind its cache |
| Fixed per-step overhead (tools 5.8k + system 1.8k) | cached after the first read | cheap locally — unless the cache is invalidated |

So on local models the levers are, in order: **fewer generated tokens, fewer steps, smaller results entering the
context, no cache invalidations, and parallel tools.** Every idea below is judged by those.

## Goals (per task, eval suite, local 35B)

| Metric | Target |
|---|---|
| Wall time per task | **−40%** |
| Generated tokens per task (incl. thinking, plans, checklist calls) | **−40%** |
| Prompt tokens prefilled per task (new tokens actually read) | **−50%** |
| Full re-reads (cache invalidations) per task | **≤ 1** (compaction only) |
| Task success | **no drop** |

Constraints: general-purpose only (no tuning to test tasks); keep the cache-stable design (same tool list every step);
anything that rewrites earlier history happens only at compaction, which already summarises in place and reuses the
cache.

## Phase 0 — Measure (≈ ½ day)

1. **Per-step instrumentation** from llama.cpp `timings` (`prompt_n`, `cache_n`, `prompt_ms`, `predicted_n`,
   `predicted_ms`) and tool durations, logged per step with a step type: *work / checklist / plan / decision / think /
   nudge-recovery*. Flag full re-reads (`cache_n` ≈ 0 on a long prompt).
2. **A per-task summary** in the turn stats: prefill s, generation s, tool s, re-reads, tokens generated by step type.
3. **Baseline eval run** on the local 35B (and one 9B) with `evals/agent_eval` — 22 tasks; needs the GPU, so run when
   the app is idle. Re-run after every phase; keep a change only if success holds and time/tokens drop.

## Phase 1 — Generate fewer tokens (largest local win, ≈ 1 day)

1. **Plans sized for local speed.** Cap the written plan at ~600 tokens (today's budget 8,192 ≈ up to 7 min on the
   35B): goal, milestones, tools per milestone, known dead ends — no prose. The 100-token plan decision stays (≈ 5 s).
2. **Checklist without extra calls.**
   - Required only when the plan decision says multi-step; simple requests run without one.
   - Let progress ride along: a short optional `progress` field accepted on any tool call (e.g. `"1.2 done"`) that
     the harness applies to the checklist — no separate `update_tracker` generation for routine ticks.
   - Check-ins become a reminder line, not a forced step; bounced/no-op updates are merged silently (no refusal
     round trip).
   - Compact checklist calls: accept `updates` only (no re-sending goal/milestones), cap at ~150 output tokens.
3. **No narration.** Instruct "call the tool directly; no 'Let me…' preamble"; strip and don't store preambles. At
   20 tok/s, a 40-token preamble per step is 2 s × every step.
4. **Thinking only where it pays.** Keep Adaptive, but lower the default budget for routine judgment (e.g. 512) and
   keep 1k for first move / failures / final answer; measure success vs. time per budget in the eval.
5. **Output caps per step type** (`max_tokens`): checklist ~150, tool-call steps ~600 (code tools excepted),
   final answers uncapped.

*Expected:* −40% generated tokens; on the 35B that is the single biggest wall-time saving.

## Phase 2 — Fewer, faster steps (≈ 1 day)

1. **Parallel read-only tools.** When a step makes several read-only calls (web_search, web_fetch, read_file,
   read_document, list_dir, find_files, search_text, calculate, memory_search, query_data), run them concurrently and
   append results in order. Writes, shell, browser and approvals stay sequential. Four page-reading searches:
   ~90 s → ~25 s.
2. **Encourage batching** in the prompt and guides: "several independent lookups → one step with several calls" and
   `web_fetch(urls=[…])` / `web_search(queries=[…])` (already available).
3. **Hybrid executor where it pays:** routine steps on a small fast model (MiniCPM / a 2–4B) only when measured faster
   end-to-end — the executor's prefill of its own view and hand-offs cost time; decide from Phase 0 numbers.

## Phase 3 — Smaller context growth (≈ 1 day)

On a hybrid-cache model, rewriting old results means a full re-read, so the economy has to happen **when results
enter** the context, and at compaction.

1. **Compact results at entry.** Tool results go into the history as a tight view; the full text is saved to a file
   (already done) and referenced:
   - `web_search`: passage budget ~3.5k chars (from ~7k), `pages` default 4; `web_fetch` multi-page ~4k total;
     `read_file` / `read_document` default windows trimmed with clear "read more with offset" hints.
   - Strip boilerplate from page text (navigation, cookie banners, repeated headers) before ranking.
2. **De-duplicate:** a page or file already read in the chat returns a pointer to the earlier result.
3. **Compaction tuned for prefill speed:** the in-place summary (cache-reusing) triggers earlier on slow-prefill models
   (e.g. at ~50k instead of ~98k) so every later step reads less; summary length capped (~1.5k tokens). Old tool
   results are digested *as part of* the compaction, the one moment a rewrite is already paid for.

*Expected:* context per step on long research tasks ~70k → ~30k; each new step prefills ~50% fewer tokens.

## Phase 4 — Keep the cache valid (≈ ½ day)

1. **Audit every source of prompt-start changes:** tool list (must stay identical), system prompt (date/time, memory
   block, instructions — anything that changes mid-chat), recalled memories, enabled-tool notes. Move volatile parts
   into the end-of-prompt reminder.
2. **Log and alert** on unexpected full re-reads (Phase 0 flag) so regressions show immediately.
3. **Investigate llama.cpp context checkpoints** for hybrid/recurrent models (`--ctx-checkpoints` in recent builds):
   if available in this build, a rollback to a checkpoint replaces some full re-reads.

## Phase 5 — Raw throughput tuning (≈ ½ day, benchmark-driven)

1. **Prefill speed:** benchmark `-b`/`-ub` (e.g. 512 → 1024/2048) with `--n-cpu-moe`; MoE models with CPU-side experts
   often prefill much faster with larger micro-batches. Keep the fastest setting that still fits VRAM.
2. **Generation speed:** compare KV cache q8_0 vs f16 at the working context, flash attention on, thread count for the
   CPU experts; check MTP/speculative decoding availability for each model.
3. **Warm-ups:** preload the passage-ranking embedding model and the sandbox at app start (first use costs ~10 s).
4. **Tool timeouts:** browser fallback ≤ 20 s per page; stream idle timeout ~90 s with one retry.

## Phase 6 — Fixed overhead (≈ ½ day, lower priority locally)

Cached once per chat, but it fills the window and is re-read after every invalidation and at chat start:
tool descriptions 5.8k → ~3.5k (usage detail moves to guides; `update_tracker` 347, `python_sandbox` 302 first),
system prompt 1.8k → ~1.1k, nudges consolidated into one compact reminder and ablated in the eval.

## Order, effort, impact (local)

| # | Change | Effort | Wall time | Tokens | Risk |
|---|---|---|---|---|---|
| 0 | Instrumentation + baseline eval | ½ d | – | – | none |
| 1.1 | Plan cap ~600 tokens | 1 h | **high** | high | plan quality — eval |
| 1.2 | Checklist via `progress` field, adaptive requirement | ½ d | **high** | high | small models drift → keep for small profile |
| 2.1 | Parallel read-only tools | ½ d | **high** | – | result ordering |
| 3.1 | Compact results at entry | ½ d | medium | **high** | less detail → "read more" hints |
| 1.3–1.5 | No narration, thinking budget, output caps | ½ d | medium | medium | caps cutting real work → per step type |
| 3.3 | Earlier in-place compaction | 1 h | medium | high | summary quality |
| 4 | Cache-validity audit | ½ d | medium (avoids 90 s re-reads) | – | low |
| 5 | Batch-size / KV / warm-up tuning | ½ d | medium–high | – | VRAM fit |
| 6 | Schema / prompt / nudge diet | ½ d | low | low | behaviour changes → eval |

Recommended sequence: **0 → 1.1 → 2.1 → 1.2 → 3.1 → 5 → 4 → 1.3–1.5 → 3.3 → 6**, re-running the eval after each.

## Success check

On the local 35B (and a 9B spot check), versus the Phase 0 baseline: success equal or better, wall time −40%,
generated tokens −40%, prefilled tokens −50%, at most one full re-read per task.

*API models benefit from the same changes (fewer steps, smaller context) but are not the optimisation target.*
